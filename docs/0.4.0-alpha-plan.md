# 0.4.0-alpha: project-authored startup screens

Status: private development, based on published 0.3.0-alpha. No 0.4 release or
public deployment is authorized by this document. Existing published archives
and the current runtime behavior remain unchanged.

## Contract and scope

A project opts into a separate Luau entry point. The web build executes its
loading and failure functions in separate restricted build sessions and exports their renderer trees
to initial HTML and CSS. No author Luau is translated to JavaScript, shipped as
startup bytecode, or executed before the application VM starts. The reference
website exercises this platform feature; it must not own its implementation.

The initial output subset is Screen, Column, Row, Text, Image, Shape, Divider
and Link, with existing component validation, typography and declared project
assets. The root is one Screen. Links use existing supported HTTPS URLs and
must work without application routing. No raw HTML, CSS or JavaScript imports
are added. Unsupported components or properties fail the build.

The startup profile rejects Motion and general event handlers. The failure
state additionally admits a Button with the platform-owned startup.retry action. Existing Motion
descriptors include tween/sequence timing and easing semantics; CSS export is
an independent gate requiring equivalent timing, repeat and reduced-motion
behavior. Do not introduce a second animation API merely to animate a loader.

Ordinary pure Luau computation runs only at build time. The execution profile
must explicitly admit standard functions needed by the UI/assets SDK and
project helpers. It must exclude clocks, environment access, OS facilities,
coroutines, GC controls, host capabilities, dynamic loading and unseeded random
state. The explicit global/member allowlist now exists in the new VM source
profile; the installed 0.3 runtime does not include it. No source-text
denylist is an adequate substitute for runtime enforcement.

Dependencies execute under the same profile from their first instruction.
They cannot reach unrestricted globals through require, shared tables, closure
captures or environment mutation. Execution must have enforced time and memory
budgets, including a supervisor capable of stopping an infinite loop. The
existing documentation prerenderer is not this security boundary.

Platform-owned bootstrap handles application readiness, errors and retry. The
screen is removed only after the first successful render and initialization of
interaction handling, with no minimum display delay. Failure and disabled-JS
paths retain readable content. Responsive styling must work without the application VM. Startup uses one
project-authored palette; automatic theme selection is outside 0.4 scope by
user decision. The running application retains its theme settings. Native pre-WebView splash integration is outside this web
milestone and must not be implied by web verification.

## Implementation order and release gates

1. Admit the static output subset with negative tests (initial implementation).
2. Audit SDK global dependencies; implement and test the restricted VM profile,
   time/memory bounds, alias/import escapes and failure cleanup.
3. Add optional manifest entry, analyzer/check integration and transactional web
   export using the existing renderer. Projects without an entry stay compatible.
4. Add platform bootstrap lifecycle, accessible failure/retry and one authored palette.
5. Adopt the feature in a standalone example and the reference website. Test
   no-JS, blocked/slow/failed Wasm, warm/cold loads, narrow screens and motion off.
6. Measure first visible content and interactive readiness separately. Do not
   represent a faster splash as a measured improvement in VM startup time.
7. Run security review of the final diff before public promotion, including
   execution isolation, paths/symlinks, HTML/CSS/URL injection, asset admission,
   CSP, bootstrap races and preserved output after a failed build. Validate
   fixes and run release CI against the exact candidate. A Daybreak review can
   supply additional independent evidence when available.

`platform/packaging/startup-tree.mjs` validates output only. The new VM source
has a separate startup session constructor, filtered library tables and a
32 MiB Luau allocation budget. `run-startup-bundle.mjs` supervises the worker
with a 5-second default hard deadline, bounded output and Node heap. The Wasm
build retains its 128 MiB linear-memory ceiling. These are separate limits,
not a claim that total operating-system process memory is 32 MiB.

The current source-build and runtime identities are phase5-alpha-9. Published
release archives remain untouched. An old binary fails closed when requested
to run a startup profile. The newly compiled local Wasm passes real execution
tests for restricted imports, unchanged application globals, infinite-loop
termination and excessive allocation. Run them with:

```sh
node --test platform/tests/startup-execution.mjs platform/tests/startup-web.mjs
```

The pipeline now accepts `startup.entry` in the project manifest and exports
HTML/CSS in web builds. See [startup screens](startup-screens.md) for the current
integration and verification boundary. The standalone example is verified in
the browser; reference-site loading and authored failure screens are integrated; automatic startup theme selection is intentionally deferred.
Runtime artifact admission is complete for private development; see
[the evidence boundary](runtime-startup-admission.md). Complete module escape testing and final security
review remain release gates. Pure operations do not guarantee byte-identical
output when authors stringify object identities or rely on table traversal
order; reproducibility needs explicit tests during export integration.
